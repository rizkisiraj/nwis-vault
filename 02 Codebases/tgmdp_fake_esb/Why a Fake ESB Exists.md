# Why a fake ESB exists: test doubles and contract testing at system level

Up: [[tgmdp_fake_esb]] · [[System Overview]]

## The constraint that created it

The real TIBCO ESB lives inside Taiwan Mobile's network. The team that rebuilt TGMDP works mostly outside it. Their developer laptops, the `orbit-poc` GitLab and the trial servers cannot reach `172.x` ESB hosts. Even inside, the ESB's partner systems (NWIS, AMS, IDM) are shared and slow to change, and test accounts are scarce. The backend's own notes say NWIS flows sometimes have skip flags "for local dev where FakeESB doesn't grant test accounts" (`tgmdp_backend/CLAUDE.md:206-213`).

Without a stand-in, nobody can run a module end-to-end until UAT. Bugs in the integration layer, which is most of what this system does, would surface weeks late. The fake ESB moves that feedback to the developer's laptop.

## A test double, scaled up

In unit tests, a **test double** replaces a collaborator object. `tgmdp_jobs` does this for the ESB with Mockito:

```java
// tgmdp_jobs/src/test/java/com/taiwanmobile/tgmdpscheduler/job/impl/mdp/SyncOrgDataTest.java:83-93
when(idmEsbSoapService.getPort()).thenReturn(idmPort);
when(idmPort.syncDepartment(any(Holder.class), any(AccountReq.class)))
        .thenAnswer(invocation -> {
            Holder<CommonHeader> header = invocation.getArgument(0);
            header.value.setStatus("S");
            header.value.setTransactionId("TXN-TEST-001");
            return response;
        });
```

This is fast and exact, but it never builds an XML envelope, never touches WS-Security, never resolves a namespace, and never crosses a socket. The fake ESB is the **same idea one level up**: it replaces a whole *system* behind a real network endpoint. So the code under test runs for real, including CXF, JAXB, the HTTP client, timeouts and logging interceptors. Only the far side is fake.

```mermaid
flowchart TB
    subgraph Unit test, Mockito
        J1[SyncOrgDataService] --> M1[mock IDMPortType]
    end
    subgraph System test, fake ESB
        J2[SyncOrgDataService] --> C2[CXF client + WSS4J + logging] -->|HTTP/SOAP| F2[tgmdp_fake_esb :8085]
    end
    subgraph UAT
        J3[SyncOrgDataService] --> C3[CXF client] -->|HTTP/SOAP| E3[real TIBCO ESB] --> I3[IDM]
    end
```

The vocabulary for test doubles is worth knowing:

| Kind | Meaning | In tgmdp_fake_esb |
|---|---|---|
| **Stub** | Returns canned answers | Most SOAP endpoints. `IdmSoapEndpoint` replies `"addAccount success"` to everything (`endpoint/IdmSoapEndpoint.java:29-33`). |
| **Fake** | A working but simplified implementation | `MrmController`, `WhController` and `*MockService` generate plausible ids, lists and dates. |
| **Spy / recorder** | Records what it was called with | Every endpoint logs the full request XML (`MdpEndpoint.logRequest`, `:173-176`). Your assertions are "read the fake's log". |
| **Fault injector** | Fails on demand | The `X-FAKEESB-STATUS` header (`AmsToEsbController.java:36-42`, and every WPU endpoint). |

This sits in the middle of the [[Testing Pyramid]]: slower and broader than [[Unit Testing]], faster and safer than UAT. See [[Mocking]].

## Contract testing at system level

A **contract** is the agreement about message shape: element names, namespaces, required fields, formats and status codes. TGMDP's contracts are the WSDLs and XSDs plus the REST interface specs. The fake ESB tests that contract in three ways.

1. **Same WSDL, different implementations.** The fake serves the real WSDL files (`src/main/resources/wsdl/`) through Spring-WS. The clients are generated by CXF from WSDLs of their own. If a client sends `syncTicketByDate` in the wrong namespace, Spring-WS's `@PayloadRoot` finds no endpoint and returns a SOAP fault. The namespace contract is enforced.
2. **Bean Validation as an executable spec.** `B1EsbRequest` turns the B1 spec into annotations (`@Pattern(regexp="\\d{4}/\\d{2}/\\d{2} \\d{2}:\\d{2}") FcTime`, `@Size(max=15) TicketNo`). A client that drifts from the spec gets a `20002` from the fake *before* it ever reaches UAT. See [[Validation]].
3. **Legacy behaviour reproduced.** The fake copies quirks the client depends on, for example the always-present `RES_REPAIR` array (`AmsToEsbController.java:76-80`). This is consumer-driven thinking: the fake's job is to behave like the thing the consumer was *written against*.

This is a lightweight cousin of consumer-driven contract testing (tools like Pact). The big difference: here **nobody verifies the fake against the real ESB**. The contract is checked on the consumer side only. See [[Contract Testing]].

## Where the fake lies to you

A fake that drifts from reality is worse than no fake, because it gives false confidence. These limits are visible in the code today:

| Gap | Evidence | Consequence |
|---|---|---|
| WS-Security is never checked | All ESB paths `permitAll`, no WSS4J interceptor (`config/SecurityConfig.java:33-55`; also `tgmdp_backend/CLAUDE.md:215-220`) | Wrong account, wrong password or clock skew all "work" locally and fail in UAT with `wss4j SecurityError`. |
| Simulated timeout isn't a timeout | `X-FAKEESB-STATUS: F` returns *immediately* with HTTP 200 and `Status:"F"` (`AmsToEsbController.java:100-117`) | Client read-timeout handling is never exercised. The backend uses a dead-port test for connection failure instead (`OpenWorkTicketApiB1NegativeTest`). |
| Header status vocabulary differs | Fake MDP header says `status=10001` (`endpoint/MdpEndpoint.java:205-208`). Jobs' `SyncOrgDataService` checks `"S"` (`:69`), and the backend's own inbound replies `S`/`F`. | A consumer that branches on status could take the failure branch against the fake. Whether the real MDP service sends `S` or `10001` can't be told from this repo. |
| Some ops missing | IDM `syncDepartment` (ESB IDM service used by `SyncOrgData`) is not implemented. Only the direct IDM WebAccount ops are (`IdmSoapEndpoint`). | That job can't be run end-to-end against the fake. |
| Inbound trigger paths drift | Triggers POST to `/NWIS_ADS/services/FTSService` and `/BTSService` (`InboundTriggerController.java:109,156`), but the backend publishes `/FTSSoapHttpService` and `/BtsSoapHttpService` (`tgmdp_backend/.../config/CxfConfig.java:158,197`) | Read from the code, not run: those triggers would 404. MDP, AMS, ACPT, SKP and DataCenter paths do match. |
| Static ids in triggers | `putSyncFile` always sends `FAKEESB-MDP-SYNC-001` | It only ever tests the "transactionId not found" branch (see [[Trace - SyncTicketAllData ESB Round Trip]]). |

The general lesson: **a fake ESB proves wiring and shape, not behaviour**. Use it to answer "does my request look right, does my parser handle the response, does my error mapping work". Do not use it to answer "does NWIS accept this" or "are my credentials right". The backend's health check reporting `esb=FakeESB` vs `RealESB` exists so nobody confuses the two after a deploy (`tgmdp_backend/docs/Development_Setup.md:529-539`). See [[Environment Separation]] and [[Feature Flags and Mock Toggles]].

## How to keep a fake honest

Practices this repo partly follows and could adopt fully:

- **Serve the real contract files**, copied and not hand-retyped. ✔ The WSDLs are copied in.
- **Generate the fake's request DTOs from the same spec** the client uses, so both sides drift together, or not at all.
- **Record and replay**: capture real ESB traffic in UAT (jobs already writes structured `OUTBOUND` logs with credentials redacted), and turn the samples into fake responses.
- **Contract tests in CI**: a test in the backend's build that boots the fake and asserts each client gets a parseable answer. This would have caught the FTS/BTS trigger path drift.
- **Fault injection that really faults**: add `X-FAKEESB-DELAY-MS` to sleep, and a mode that closes the socket.
